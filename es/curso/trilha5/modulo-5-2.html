1

📖 El manual de estilo que el agente lee por sí solo

¿Eres nuevo aquí? Una skill (ya presentada en la Ruta 3) es un conjunto de instrucciones guardado en un archivo que el agente consulta por su cuenta antes de hacer cierto tipo de trabajo, como una ficha de procedimiento que un empleado saca del cajón antes de empezar una tarea que ya tiene una «forma correcta de hacerse» en la empresa. Una skill de diseño es este mismo mecanismo, especializado en front-end: guarda la paleta de colores, la tipografía, el espaciado, el estilo visual y los principios que definen lo que es «bonito» para ti, no para todo internet.

Piensa en un estudio de arquitectura de verdad: existe una carpeta física (o un PDF) llamada «manual de identidad visual» — colores exactos en código hexadecimal, fuentes aprobadas, márgenes mínimos, ejemplos de lo que se puede y lo que no se puede hacer. Todo nuevo pasante lo lee antes del primer proyecto. Nadie vuelve a explicar cada color en una reunión cada vez. La skill de diseño es exactamente ese manual, solo que el «pasante» es el agente y lee el manual por su cuenta, al inicio de cada tarea de front-end — sin que tengas que volver a escribir nada.

💡 Concepto principal

La skill de diseño aborda exactamente la causa 1 del módulo 5.1: la falta de referencia que hacía que el modelo cayera en la media estadística de su entrenamiento.

  • •Sin una skill: el agente llena el vacío con lo «más visto» — azul, blanco, centrado.
  • •Con una skill: el agente llena el vacío con lo que TÚ definiste —tu referencia, no el promedio de todas.

2

⚖️ «Haz un sitio bonito» vs. una solicitud guiada por una skill

"Crea un sitio bonito" es una solicitud vaga porque "bonito" no tiene una definición fija: cada persona del planeta con la que se entrenó ese modelo tiene una idea diferente de lo que es "bonito", y el modelo calcula el promedio de todo, que es justamente ese "olor a IA" del módulo anterior. En cambio, una solicitud respaldada por una skill de diseño no necesita decir "bonito" ni una sola vez: la skill ya define de antemano qué significa "bonito" para ti: qué paleta usar, qué tipografía, qué espaciado y qué tono (¿serio?, ¿divertido?, ¿lujoso?, ¿artesanal?). El agente ya no inventa nada en lo visual: aplica la regla que ya existe.

Leyenda: arriba, sin ningún manual, el pedido vago cae directamente en el promedio estadístico. Abajo, el agente tiene la costumbre de abrir la skill de diseño ANTES de escribir cualquier front-end: incluso un pedido corto ya sale con la paleta, la tipografía y el tono correctos, porque la decisión ya estaba tomada en el manual.

🔍 Por dentro

  • "Bonito" sin definición: una palabra que cada entrenamiento interpreta como el promedio de todo lo que ya vio.
  • "Bonito" con una skill: una decisión tuya, escrita una vez y aplicada siempre: deja de ser una opinión del modelo y se convierte en una regla del proyecto.
3

🧩 La anatomía de una skill de diseño

Toda skill (recordando la Ruta 3) tiene una descripción/activador — la frase breve que le indica al agente CUÁNDO consultar ese archivo, sin tener que leerlo completo para decidirlo. En una skill de diseño, el activador es algo como «úsala antes de crear, rediseñar o revisar cualquier página, componente o interfaz». Eso hace que el agente abra el manual por su cuenta, incluso cuando solo pediste «crea un formulario de contacto» sin mencionar «diseño» ni «skill» ni una sola vez.

Después del disparador vienen las reglas de estilo propiamente dichas: paleta de colores (con los códigos hexadecimales exactos, no un "azul" o "verde" vago), la tipografía (qué fuentes usar, de qué tamaño, para títulos y para el texto corrido — tipografía es solo el nombre técnico para “la elección y el estilo de las letras”), espaciado (cuánto espacio hay entre elementos, esquinas rectas o redondeadas) y el tono visual general (¿serio y corporativo? ¿divertido y colorido? ¿minimalista y sofisticado?). Por último, una buena skill incluye ejemplos — fragmentos de código o descripciones concretas de "esto está bien" y "esto está mal", porque los ejemplos concretos guían mejor que las reglas abstractas.

✓ Lo que aporta una buena skill de diseño

  • ✓Disparador claro: cuándo invocarlo (antes de CUALQUIER front-end)
  • ✓Paleta con códigos hex exactos, no nombres de colores vagos
  • ✓Tipografía definida (fuente de títulos, fuente de texto, tamaños)
  • ✓Ejemplos de "correcto" e "incorrecto" lado a lado

✗ Lo que convierte una skill en una skill débil

  • ✗"Usa colores agradables y modernos" (tan vago como el pedido original)
  • ✗Ningún disparador: la skill existe, pero el agente nunca sabe cuándo abrirla
  • ✗Reglas que cambian de un proyecto a otro sin que nadie las revise

💡 Consejo práctico

Prueba rápida para saber si tu skill está bien: lee en voz alta la regla de color. Si puedes decir el código hexadecimal de memoria, es lo bastante concreta. Si la frase es algo como «colores que transmitan confianza», todavía es demasiado vaga; reescríbela con los hex exactos.

4

🌐 Skill global instalada una vez vs. reescribir cada conversación

¿Eres nuevo aquí? "Global vs. proyecto" se trata de DÓNDE se guarda la skill y QUÉ proyectos pueden verla (tema que se profundiza en el módulo 3.5, pero que volvemos a abordar aquí porque es central). Una skill de proyecto vive dentro de la carpeta de ese proyecto específico y solo sirve allí. Una skill global queda instalada una sola vez en un lugar de tu computadora que todos los proyectos de Claude Code detectan automáticamente; funciona en cualquier carpeta que abras, sin tener que copiar el archivo de nuevo en cada proyecto nuevo.

La diferencia práctica es enorme. Sin una skill global, cada vez que abres un proyecto nuevo —el sitio de la panadería, el dashboard de la consultora, la landing page del curso— tienes que volver a explicar desde cero: «usa este color, esta fuente, este espaciado». Eso cansa, es fácil olvidar algún detalle y el resultado varía de un proyecto a otro, aunque quisieras el MISMO estilo en todos. Con la skill instalada globalmente, guardas el manual una sola vez y cada proyecto nuevo —incluso dentro de seis meses, incluso uno que hoy ni te imaginas— ya empieza con esa misma referencia.

📊 Dónde vive cada tipo y quién lo ve

  • Skill de proyecto: dentro de la carpeta del proyecto: solo quien abra ESE proyecto lo verá. Ideal para una regla específica de UN cliente o marca.
  • Skill global: instalada una vez en tu cuenta: TODO proyecto que abras la ve. Buena para «tu forma predeterminada de hacer front-end», que siempre reutilizas.

✗ Sin skill global

  • ✗Vuelves a explicar el color, la fuente y el tono en cada conversación nueva
  • ✗Es fácil olvidar un detalle — el resultado varía de un proyecto a otro
  • ✗Cada proyecto nuevo «nace» sin ninguna referencia y vuelve a ser genérico

✓ Con skill global

  • ✓Escribes el manual una sola vez y todos los proyectos nuevos ya nacen consultándolo
  • ✓Consistencia automática entre distintos proyectos, sin esfuerzo adicional
  • ✓Funciona dentro de seis meses, en un proyecto que hoy ni te imaginas

5

🎯 Invocar la skill antes de escribir el front-end: el hábito

La disciplina que separa una skill útil de una skill olvidada cabe en una sola frase: invocar siempre la skill de diseño ANTES de escribir cualquier código de front-end, nunca después. Si dejas que el agente escriba primero el componente y «lo revise con la skill» después, ya habrá dedicado esfuerzo a construir basándose en una suposición genérica: es trabajo doble. El hábito correcto es: llega un pedido de front-end → se abre primero la skill → solo entonces se escribe el código, ya con la referencia correcta.

Objetivo: probar, en tu propio entorno, si una skill de diseño instalada globalmente cambia el resultado de una solicitud sencilla de un componente, sin que tengas que mencionar el color, la fuente ni el estilo en ningún momento, porque eso ya debería venir de la skill.

Si ya tienes una skill de diseño instalada globalmente, el resultado debería usar su paleta y tipografía, sin un «Get Started» azul genérico. Si todavía no tienes ninguna skill instalada, probablemente el agente te avisará que no encontró ninguna; eso ya confirma la lección: sin un manual que consultar, vuelve a hacer conjeturas. (Los módulos 5.6 y 5.7 explican paso a paso cómo instalar tu propia skill de diseño, con la carpeta de marca completa.)

✅ Cómo verificar

  • Verifica si el agente mencionó al inicio de la respuesta que consultó una skill de diseño (o avisó que no encontró ninguna instalada).
  • Abre el HTML generado: ¿los colores coinciden con una paleta específica o sigue apareciendo el azul y blanco predeterminado?
  • Repite la misma solicitud en otra carpeta de proyecto — si la skill es global, el resultado debe tener el mismo aspecto en las dos carpetas.

⚠️ Atención

Tener la skill instalada no es lo mismo que hacer que el agente recuerde usarla por su cuenta cada vez. Si el resultado sale genérico incluso con la skill instalada, el problema suele ser un disparador débil (una frase demasiado vaga para activar la lectura): revisa la descripción de la skill, no la solicitud.

6

🗺️ Lo que la skill NO resuelve por sí sola

La skill de diseño aborda la causa 1 del módulo 5.1: la falta de referencia, pero no aborda la causa 2: nadie obliga al agente a MIRAR de verdad el resultado antes de entregártelo. Una skill bien escrita reduce mucho el «aire de IA» porque el agente parte de buenas decisiones, pero no reemplaza una mirada crítica al resultado final: el CSS puede estar técnicamente bien y aun así verse desalineado, apretado o con poco contraste en una pantalla real. Justamente esa segunda mitad es lo que resuelve el siguiente módulo.

🎯 Concepto principal

  • •Skill de diseño (5.2) = referencia escrita que se consulta antes de programar.
  • •Bucle de screenshot (5.3) = el agente toma una captura, revisa el resultado y lo corrige — después de programar.
  • •Las dos juntas completan el ciclo: la referencia correcta ANTES, el ojo crítico DESPUÉS.
