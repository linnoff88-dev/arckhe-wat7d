MÓDULO 3.4

🎯 La descripción es el detonante

Entre 20 skills instaladas, ¿cómo sabe el agente cuál usar? No lee el `skill.md` completo de cada una: lee un único campo, breve, de cada una. Este módulo trata sobre ese campo: a description, el texto que decide si tu skill se encuentra o se ignora.

1

🔎 El único texto que cuenta al momento de elegir

¿Eres nuevo aquí? Cuando tienes varias skills instaladas, el agente no lee el `skill.md` completo de cada una todo el tiempo: eso costaría muchos tokens (la unidad que mide cuánto texto se procesó, vista en el módulo 0.1). Lo que revisa para decidir qué skill coincide con tu pedido es solo la description — la frase breve que aparece en el front matter, al inicio del archivo.

Es exactamente cómo funciona en la práctica la carga en 3 niveles del módulo 3.2: el nivel 1 es nombre+descripción, y SOLO con este nivel 1 el agente decide si abre la skill completa (nivel 2). Si la descripción no convence, ni siquiera se considera la skill, sin importar lo bueno que sea el paso a paso que contiene. Es la etiqueta del cajón: si no describe bien lo que hay dentro, nadie abrirá ese cajón en el momento adecuado.

💡 Concepto principal

La description no describe QUÉ es la skill: describe CUÁNDO usarla.

  • •Se compara con el pedido del usuario; no se lee de forma aislada.
  • •Las palabras concretas que diría el usuario pesan más que la jerga técnica interna.
2

⚖️ Vaga vs. específica

Una descripción vaga habla del área general; una buena habla de la SITUACIÓN concreta que la activa. Compara: "ayuda con documentos" no dice nada que ayude a decidir: casi cualquier solicitud "encaja" con eso, o ninguna encaja de verdad. En cambio, "genera un PDF de contrato a partir de un modelo de Word cuando el usuario pida 'contrato', 'generar PDF' o 'modelo de documento'" le da al agente palabras clave reales para comparar con la solicitud.

✗ Descripción vaga

  • ✗"Ayuda con documentos."
  • ✗"Herramienta para informes."
  • ✗"Skill de automatización general."

✓ Descripción específica

  • ✓"Genera un PDF de contrato a partir de una plantilla de Word cuando el usuario pida 'contrato' o 'generar PDF'."
  • ✓"Arma el informe mensual de ventas en PDF cuando el usuario diga 'cierre del mes'."
  • ✓"Programa una tarea recurrente cuando el usuario diga 'todos los días', 'todas las semanas' o 'ejecútalo solo'."

✨ Consejo práctico

Escribe la description como si respondieras "¿cuándo debo abrir este cajón?", no "¿qué hay dentro de este cajón?". La pregunta correcta cambia todo el texto.

3

⌨️ /comando explícito vs. lenguaje natural

¿Eres nuevo aquí? Hay dos maneras de activar una skill. La primera es escribir el /nome-da-skill directo: como llamar a alguien por su nombre exacto, sin margen de error, porque estás apuntando al `name` del front matter. La segunda es escribir en español normal ("genera el informe del mes") y dejar que el agente HAGA COINCIDIR tu intención con la description de alguna skill instalada, como un recepcionista que escucha tu pedido y sabe a qué departamento enviarte.

Leyenda: el pedido en portugués entra por la izquierda; el agente lo compara con la descripción de cada skill instalada (resaltadas en el centro) y activa la que mejor coincide. En el ejemplo, la skill C.

🔍 Por dentro

  • /comando: cero ambigüedad — elegiste la skill por su nombre, punto final.
  • Lenguaje natural: depende por completo de la calidad de la description de TODAS las skills instaladas, no solo de la tuya.
  • La mayoría de las skills bien hechas funciona en los dos modos porque el `name` es claro Y la `description` es específica.
4

⚠️ Errores comunes en la description

Se repiten tres trampas: (1) demasiado genérica: palabras que sirven para cualquier skill del dominio; (2) centrada en «qué es la skill» («herramienta de PDF») en vez de «cuándo usarla» («genera un PDF de contrato cuando el usuario diga X»); (3) competencia: dos skills con descripciones parecidas que compiten por la misma solicitud, lo que hace que el agente elija mal o dude entre ambas.

Evolución de una description: mala → mejor → buena

# Ruim
description: Ajuda com relatórios da empresa.

# Melhor
description: Gera relatórios em PDF a partir de planilhas Excel.

# Boa
description: Gera o PDF do relatório mensal de vendas a partir da
  planilha vendas.xlsx quando o usuário pedir "relatório mensal",
  "fechamento do mês" ou "PDF de vendas". Nêo usar para relatórios
  de outro tipo (ver skill "relatorio-financeiro-anual").

⚠️ Atención

La versión «buena» de arriba hace más que describir: también indica qué NO debe cubrir y remite a otra skill. Eso resuelve la competencia antes de que se convierta en un problema (ver el tema 5).

5

🥊 Competencia entre skills similares

Cuando dos skills compiten por la misma situación —por ejemplo, «skill-relatorio-vendas» y «skill-relatorio-geral» con descripciones parecidas—, el agente puede confundirse, elegir la incorrecta o hacerte demasiadas preguntas para desempatar. La solución es DIFERENCIAR: cada descripción debe dejar claro el límite que la separa de la otra, no solo lo que hace. Piensa en dos letreros de tiendas vecinas: si ambos dicen «vende comida», el cliente no sabe cuál es la pizzería y cuál la heladería.

t=0

El usuario escribe: "arma el informe de ventas de julio".

t=1

El agente recorre en paralelo las descripciones de todas las skills instaladas, no una por una en orden.

t=2

Si dos descriptions coinciden igual de bien, el agente puede elegir la «más específica» o detenerse y preguntar; su comportamiento no siempre es predecible.

t=3

Con descriptions bien diferenciadas, la coincidencia es única e inmediata —sin vacilación.

✗ Descriptions en conflicto

  • ✗"Genera un informe de ventas." (skill A)
  • ✗"Genera un informe mensual." (skill B)

✓ Descriptions diferenciadas

  • ✓"Genera un informe de ventas por región, en Excel." (skill A)
  • ✓"Genera un informe financiero consolidado del mes, en PDF." (skill B)
6

🧪 Probar si la description se activa correctamente

No necesitas adivinar si la description funciona: puedes probarlo directamente. Abre una sesión nueva (sin contexto de la conversación anterior), escribe una solicitud en lenguaje natural como la escribiría un usuario real y fíjate si el agente reconoce y activa la skill correcta. Repítelo con 2-3 frases diferentes que describan la misma intención. Si alguna falla, el activador todavía es débil.

Copy-run — objetivo

Probar, en una sesión nueva, si la description de una skill tuya se activa con 3 frases diferentes que diría un usuario real.

Sem executar nada ainda: olhando só as descriptions das skills
que você tem disponíveis agora, me diga qual skill você usaria
para cada um destes três pedidos, e por quê:
1) "<frase 1 que um usuário real diria>"
2) "<frase 2, mesma intençêo, palavras diferentes>"
3) "<frase 3, mais indireta/informal>"
Se nenhuma skill combinar bem com algum pedido, me diga isso
também — nêo force um match.

Cómo verificar: las tres respuestas deben apuntar a tu skill <nome-da-skill>. Si alguna apunta a otra skill (o a ninguna), vuelve a la description y ajusta las palabras clave.

✨ Consejo práctico

Pídele a alguien que NO haya escrito la skill que describa, con sus propias palabras, cuándo la usaría; si su frase no coincide con tu description, la description es la que está mal, no la persona.

Verificación rápida (opcional): ¿qué lee el agente PRIMERO para decidir qué skill usar entre varias instaladas?

Ejercicio rápido:

Toma una description tuya (o escribe una nueva para alguna tarea repetitiva) y reescríbela tres veces: una enfocada solo en «qué es», otra enfocada en «cuándo usarla» y la versión final que combine ambas — compara cuál te resulta más fácil de reconocer.
