🔎 Observabilidade: ler o painel e achar a falha no log

Sua automação está no ar. Mais cedo ou mais tarde, algo vai falhar — e quando falhar, você não precisa saber ler código. Precisa saber ler o painel de execuções e o log: a lista de eventos que a automação foi registrando enquanto rodava. Este módulo fecha a Trilha 4 ensinando exatamente isso.

1

📺 O painel de execuções

Novo aqui? Um painel (ou dashboard) é a tela onde a plataforma de execução mostra tudo que rodou: cada vez que sua automação disparou, aparece uma linha nova — com data, hora e um status (sucesso ou falha). É o "extrato bancário" da sua automação: você não precisa entender como o banco processa por dentro, só sabe ler se a conta fechou certo.

No painel do Trigger.dev (a plataforma usada no módulo 4.6), cada execução vira uma linha clicável. Clicar nela abre os detalhes — inclusive o log, que é o assunto do próximo tópico.

Legenda: à esquerda, a lista de execuções com status colorido. À direita, o que aparece ao clicar numa execução que falhou — o log, linha por linha, mostrando exatamente onde e por que travou.

2

📜 O que é um log, de verdade

Novo aqui? Um log é a lista de eventos que a automação foi anotando enquanto rodava — tipo um diário de bordo. Cada linha registra "o que aconteceu" e "a que horas". Não é código: é texto simples, em ordem cronológica, contando a história do que a automação tentou fazer.

Você não precisa saber ler TypeScript. Precisa saber ler o log. É a frase mais importante deste módulo. O log conta a história em português (ou em mensagens claras) mesmo quando o código por trás é técnico — porque quem escreveu a task (o Claude Code, seguindo suas instruções) normalmente deixa mensagens legíveis em cada etapa importante.

💡 Conceito Principal

  • •Cada linha do log tem: horário + o que aconteceu.
  • •Linhas normais contam o progresso ("buscando...", "enviando...").
  • •Linhas de erro (normalmente destacadas em vermelho ou com a palavra "ERRO") indicam onde travou.

3

🔴 Achando a linha vermelha

Quando uma execução aparece com status de falha no painel, o processo é sempre o mesmo: clique nela, abra o log, e desça até achar a primeira linha marcada como erro. Não precisa ler tudo com atenção igual — as linhas normais só confirmam que "até aqui, tudo bem"; o que importa é onde a história muda de rumo.

Lembra do módulo 4.5? Se a automação foi bem desenhada, com retentativa, você vai ver algumas tentativas registradas no log antes do erro final — isso é normal e não significa que está tudo quebrado, significa que o sistema tentou se recuperar sozinho e não conseguiu daquela vez.

✓ Leitura eficiente do log

  • ✓Vai direto pra primeira linha marcada de erro
  • ✓Lê a mensagem ao redor pra entender o contexto (o que estava tentando fazer)
  • ✓Copia a linha de erro inteira, sem resumir de cabeça

✗ Se perdendo no log

  • ✗Tenta ler linha por linha desde o início, se cansa e desiste
  • ✗Vê uma palavra técnica e acha que precisa entender código pra continuar
  • ✗Descreve o erro de memória pro Claude Code, sem colar o texto exato

💡 Dica Prática

A maioria dos painéis de execução tem um botão "copiar log" ou permite selecionar o texto direto. Use isso — copiar o trecho exato é muito mais eficaz do que tentar resumir o erro de memória.

4

🤝 Levando o erro de volta pro agente

Achou a linha vermelha? Não precisa decifrá-la sozinho. Volte ao Claude Code, cole o trecho do log (com contexto de algumas linhas antes e depois) e peça uma investigação — ele lê código com naturalidade e traduz o problema pra você em português.

Objetivo: pedir pro Claude Code investigar uma falha real, usando o log copiado do painel como evidência — sem você precisar entender o erro técnico primeiro.

Como verificar: a resposta do agente deve apontar uma causa provável em linguagem simples (ex.: "a chave de API parece estar errada ou vencida" ou "o serviço externo demorou mais que o tempo limite") e uma ação concreta — corrigir o código, recadastrar uma chave, ou aumentar um tempo de espera. Se a resposta ficar vaga, peça: "aponte exatamente qual linha do log te fez concluir isso".

⚠️ Atenção

Ao colar um log, revise antes se ele não contém uma chave de API real por engano — alguns erros de autenticação mostram parte da chave usada. Se aparecer, apague esse trecho antes de colar em qualquer lugar, inclusive numa conversa com o agente.

5

🔄 O hábito de checagem

Observabilidade não é um evento único — é um hábito. Automação publicada sem ninguém olhando o painel de vez em quando é automação que pode estar falhando há dias sem você saber.

A boa notícia: você não precisa ficar checando manualmente todo dia. A maioria das plataformas permite configurar um alerta (por e-mail ou mensagem) que avisa automaticamente quando uma execução falha — assim o painel só precisa da sua atenção quando algo realmente pede.

1

Primeira semana: olhe todo dia

Depois de publicar uma automação nova, confira o painel diariamente até confiar que ela está estável.

2

Depois: configure alerta e relaxe

Peça ao Claude Code pra configurar um aviso automático de falha — assim você só olha quando precisa.

3

Quando o alerta chegar: log primeiro, código depois

Siga o processo dos tópicos 1 a 4 — painel, log, linha vermelha, agente.
