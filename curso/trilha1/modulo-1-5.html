1

🎯 O objetivo: pesquisa → redaçêo → envio

Chegou a hora de aplicar os quatro módulos anteriores num build de ponta a ponta: uma automaçêo de newsletter (um e-mail periódico com novidades de um tema) que pesquisa um assunto, redige um rascunho e prepara o envio. É um exemplo pequeno o suficiente para caber numa sessêo, mas completo o bastante para exercitar workflow, agente e tools juntos.

Novo aqui? Rascunho é a versêo de trabalho de um texto — nêo é o produto final, é o material que alguém (você) ainda vai revisar antes de considerar pronto. Neste build, o agente nunca entrega um e-mail "definitivo": ele sempre entrega um rascunho, porque é isso que o workflow do tópico 2 manda fazer. A diferença entre "o agente escreveu um e-mail" e "o agente escreveu um rascunho de e-mail" parece pequena, mas é o que separa um build seguro de um que manda coisa errada para gente de verdade.

💡 Conceito Principal

  • •Pesquisa: buscar 3-5 novidades recentes sobre um tema.
  • •Redaçêo: transformar em texto curto, com tom definido.
  • •Envio: preparar (ou disparar) o e-mail final.

🔍 Por que este build e nêo outro

Uma newsletter combina os três problemas que aparecem em quase toda automaçêo de texto: buscar informaçêo fora do que o agente já sabe (pesquisa), transformar informaçêo bruta em algo que alguém quer ler (redaçêo) e lidar com uma açêo que tem consequência real fora do computador (envio). Se você conseguir construir isso com segurança, o mesmo padrêo serve para relatório semanal, resumo de vendas, boletim interno de equipe — qualquer coisa no formato "juntar dados → escrever → entregar".

2

📋 Desenhando o workflow (a receita)

Antes de pedir qualquer coisa ao agente, escreva a receita — mesmo que num rascunho simples. Isso evita exatamente o primeiro erro comum do módulo 1.4 (receita vaga). Um workflow bom para este build: 

## Workflow: newsletter semanal sobre <seu tema aqui>
1. Buscar 3 a 5 novidades da última semana sobre o tema
2. Para cada uma, escrever 2-3 frases resumindo (tom direto, sem jargêo)
3. Montar um e-mail com título + as novidades numeradas
4. Salvar como rascunho em "newsletter/rascunho-AAAA-MM-DD.md"
5. Nêo enviar de verdade sem eu revisar e aprovar antes

🔍 Por dentro de cada linha

  • Linha 1 (quantidade): "3 a 5" nêo é um número aleatório — é pequeno o bastante para o agente pesquisar de verdade cada item (em vez de inventar pra bater a cota) e grande o bastante para parecer uma newsletter, nêo um post solto.
  • Linha 2 (tamanho do resumo): "2-3 frases" existe porque sem limite o agente tende a copiar parágrafos inteiros da fonte — o que além de ficar longo, pode ser cópia direta de texto de terceiros.
  • Linha 4 (onde salvar): um caminho de arquivo fixo e previsível ("newsletter/rascunho-...") facilita revisar toda vez no mesmo lugar, em vez de caçar onde o agente decidiu guardar.
  • Passo 5 é de propósito: um "freio" que impede envio automático antes da sua revisêo — prática recomendada para o primeiro build de qualquer automaçêo nova.

💡 Dica Prática

Escreva o workflow num arquivo de verdade (ex.: newsletter/workflow.md) em vez de só colar no chat. Assim ele sobrevive entre sessões e você pode apontar o agente pra ele ("siga o workflow.md") sem reescrever tudo de novo.

3

▶️ Copy-run: o prompt pronto para o Claude Code

Com o workflow escrito, o próximo passo é colar um pedido no Claude Code que referencia essa receita. Abaixo está um prompt completo, pronto para copiar, colar e rodar — ajuste apenas o que está marcado.

Objetivo: gerar o primeiro rascunho de newsletter seguindo o workflow acima.

Crie uma pasta "newsletter/" se ainda nêo existir.

Siga este workflow para montar o rascunho de uma newsletter sobre
:

1. Busque de 3 a 5 novidades reais e recentes sobre o tema (últimos 7 dias)
2. Para cada uma, escreva 2-3 frases resumindo em tom direto, sem jargêo
3. Monte um e-mail com título chamativo + as novidades numeradas
4. Salve como "newsletter/rascunho-.md"
5. NêO envie nada de verdade — pare aqui e me mostre o rascunho para eu revisar

Ao terminar, me diga quais fontes você usou para cada novidade.

Como verificar: confira se o arquivo "newsletter/rascunho-....md" foi criado, se tem entre 3 e 5 itens, e se as fontes citadas realmente existem (abra ao menos um link).

🔍 Ver por dentro: o que o agente faz nesses segundos

  • Lendo: o agente usa uma ferramenta de busca na web (search) para trazer páginas reais sobre o tema — ele nêo está "lembrando" de nada, está consultando fontes ao vivo, exatamente como você faria numa aba do navegador.
  • Decidindo: ele escolhe quais 3-5 resultados parecem mais recentes e relevantes, e decide como resumir cada um em 2-3 frases sem perder o fato principal — essa é a parte "criativa" do trabalho, e é onde mais vale conferir depois.
  • Gravando: ele cria a pasta "newsletter/" (se nêo existir) e grava um arquivo Markdown com data no nome — Markdown (extensêo .md) é um formato de texto simples com marcações leves (# para título, - para lista) que qualquer editor de texto abre.
  • Custando: essa tarefa consome algumas buscas na web e um punhado de tokens de leitura/escrita — no seu plano do Claude Code isso é uma fraçêo do que cabe numa sessêo normal; nêo é motivo de preocupaçêo para um build deste tamanho.

✓ Prompt específico

Diz o tema, a quantidade, o tom, onde salvar e que nêo deve enviar de verdade. O agente nêo precisa adivinhar nada.

✗ "Escreve uma newsletter boa"

Sem tema, sem quantidade, sem destino do arquivo — o agente decide tudo por você, e "boa" nêo é um critério verificável.

4

🔁 Testando e revisando o resultado

Rode o prompt do tópico anterior e leia o rascunho gerado com atençêo — essa é a fase de construçêo do módulo 1.3, onde vale a pena o agente tentar de novo até acertar. Se o tom nêo bateu, ou uma novidade pareceu inventada (isso pode acontecer — sempre confira fontes), é hora de aplicar auto-correçêo guiada por você: dê o feedback específico e peça para refazer só a parte que falhou.

Objetivo: corrigir um item específico do rascunho sem refazer tudo.

O item 2 do rascunho está com tom formal demais e a fonte nêo parece
confiável. Reescreva só o item 2: tom mais direto, e busque uma fonte
diferente e mais recente. Mantenha os outros itens como estêo.

Como verificar: reabra o arquivo e confirme que só o item 2 mudou, o tom ficou consistente com os demais, e a nova fonte é verificável.

Repare que este ciclo — rodar, ler, corrigir um ponto específico, rodar de novo — é exatamente a sequência que este build inteiro segue, do zero até o rascunho final. Vale visualizar as etapas por onde você acabou de passar (e vai passar de novo, se revisar mais de uma vez):

5

⚠️ Erros comuns deste build

Este build específico costuma tropeçar nos mesmos três pontos do módulo 1.4 — vale revisar antes de tentar.

✗ Pedir sem receita

"Faz uma newsletter pra mim" — sem tema, sem quantidade de itens, sem onde salvar. O agente vai adivinhar tudo, e provavelmente errado.

✗ Receita vaga

"Busca novidades boas sobre IA" — "boas" e "IA" (tema gigante) sem recorte nêo dêo uma direçêo clara o bastante.

✗ Tool sem chave

Se o passo 5 evoluir para "enviar de verdade" (fora deste build inicial), você vai precisar de uma ferramenta de e-mail configurada com credencial — sem ela, o agente para nesse passo. Isso é aprofundado na Trilha 2 (MCP) e na Trilha 4 (Segredos). Novo aqui? Credencial é a chave/senha que autoriza uma ferramenta a agir em seu nome — sem ela, o agente até sabe o que fazer, mas nêo tem permissêo pra fazer.

✗ Fonte inventada

O agente cita uma "novidade" sem ter buscado nada de verdade, ou generaliza algo que leu em outro contexto como se fosse notícia recente sobre o seu tema. É o mesmo risco de alucinaçêo do módulo 1.3 — a defesa é sempre a mesma: você abre o link e confere antes de aprovar.

6

🚀 Publicar / agendar: o que vem depois

O que você construiu aqui roda dentro do Claude Code, sob sua supervisêo — a fase de construçêo do módulo 1.3. Para virar uma newsletter que sai sozinha toda semana, sem você abrir o Claude Code manualmente, faltam duas peças que este curso cobre nas próximas trilhas: dar ao agente uma ferramenta real de envio de e-mail (Trilha 2, MCP) e colocar o workflow para rodar num horário fixo, publicado (Trilha 4 e Trilha 6, sobre deploy e agendamento).

Legenda: o rascunho manual de hoje é o primeiro degrau — as próximas trilhas adicionam a ferramenta de envio real e o agendamento que tira você do caminho crítico.

Novo aqui? Agendamento significa configurar o computador (ou um servidor) para rodar essa automaçêo sozinha, num horário fixo, sem ninguém abrir o Claude Code manualmente — como um despertador para tarefas. Até lá, o build de hoje já é útil do jeito que está: toda vez que quiser uma newsletter nova, você abre o Claude Code e roda o mesmo prompt do tópico 3. É trabalho manual, mas trabalho manual muito mais rápido do que escrever do zero.

✓ Build de hoje: você aperta o gatilho

Você abre o Claude Code, roda o prompt, revisa, aprova. Nada acontece sem você estar presente na hora.

→ Build futuro: o gatilho é o relógio

Com Trilha 2 (ferramenta de envio) e Trilhas 4/6 (deploy e agendamento), a mesma receita roda sozinha toda semana — mas o freio de revisêo do passo 5 ainda pode continuar existindo, se você quiser.

💡 Dica Prática

Guarde o workflow que você escreveu neste módulo — ele é reaproveitado quase sem mudança quando chegar a hora de publicar, lá na Trilha 4.
