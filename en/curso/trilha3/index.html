TRACK 3

🧩 Skills: teaching a process

Skill is your agent's SOP (standard operating procedure): a text file that teaches it, all at once, how to do a task you repeat often — and that the agent learns to call on its own, either through a typed command or simply by understanding that it's the right moment. In this track, you'll learn the anatomy of a skill, why having 20 of them installed doesn't slow the agent down, write your first one from scratch, and learn to sharpen the ones you already have.

Caption: the deeper the agent needs to go, the more it loads—and only when needed. That’s why having 20 skills installed doesn’t slow down the conversation: most stay idle at Level 1.

3.1 ~30 min

🧬 The anatomy of a skill

Skill = the agent's SOP (standard operating procedure). A folder, a SKILL.md with front matter, references, and scripts.

What it is:

A “skill” is a text file that teaches the agent to do a task you repeat — like a procedure manual a company gives to a new employee.

Why learn:

Without a skill, you explain the same process every time. With one, you write it once and the agent follows it on its own afterward.

Key concepts:

POP (standard operating procedure), reuse, persistent instruction.

What it is:

Each skill lives in its own named folder, containing at least one file SKILL.md and, optionally, reference subfolders and scripts.

Why learn:

Understanding the folder structure is the first step toward creating (module 3.6) and organizing your own.

Key concepts:

Skill folder, root file, optional subfolders.

What it is:

Front matter is a short block at the top of the file, between two lines ---, with pairs like name: e description: — it's the "label" the agent reads first, before opening the rest.

Why learn:

It's this label that determines whether the skill is called or ignored—the central topic of module 3.4.

Key concepts:

Front matter, metadata, structured header.

What it is:

Extra documents (inside a subfolder, for example references/) with the fine details — large tables, lists of errors, long examples — that the agent opens only if the task requires it.

Why learn:

Keeping SKILL.md concise and moving details to a reference is what makes each skill cheaper to use — the topic of module 3.2.

Key concepts:

Reference, details on demand, deep archive.

What it is:

A skill can package ready-to-use scripts (Python, Node, shell) that the agent runs instead of writing code from scratch every time.

Why learn:

An embedded script is faster and more reliable than “reinventing” the logic on every call.

Key concepts:

Embedded script, deterministic execution, WAT — tools.

What it is:

A guided walkthrough of a real installed skill — front matter, body, reference — to see how the parts work together.

Why learn:

Seeing the complete example wraps up the theory before you build your own in module 3.6.

Key concepts:

Case study, applied anatomy.

3.2 ~30 min

📶 Progressive loading in 3 levels

Name and description are always present; the full skill is loaded only when triggered, and references only when needed. That’s why 20 installed skills don’t weigh down the context.

What it is:

Context is everything the agent "has in its head" during a conversation — your message, the history, the open files. It's limited, and the fuller it gets, the more each response costs and the slower it becomes.

Why learn:

Progressive loading exists specifically to avoid filling this space with skills that aren’t being used.

Key concepts:

Context, memory window, cost per token.

What it is:

One token is a small piece of text (near a word) — the unit AI uses to "read" and charge for. In Level 1, only the name and description of each skill are always available, costing about 100 tokens each.

Why learn:

It's this inexpensive level that lets the agent “know the skill exists” without loading all of it.

Key concepts:

Token, Level 1, always resident.

What it is:

When the trigger (module 3.4) fires, the agent opens the entire SKILL.md — the complete step-by-step guide — and only then does that higher cost come into play.

Why learn:

Understanding this “only when needed” behavior explains why having lots of skills installed doesn’t slow everything down.

Key concepts:

Level 2, loaded on demand.

What it is:

The last level: reference files or scripts that the agent opens only if it needs that specific detail while working on the task.

Why learn:

This is what lets a skill have extensive documentation without costing much most of the times it’s used.

Key concepts:

Level 3, conditional reading.

What it is:

20 skills × ~100 Level 1 tokens comes to around 2 thousand fixed tokens — little compared with a context window that can handle hundreds of thousands.

Why learn:

This concrete number dispels the fear of "having too many skills installed."

Key concepts:

Aggregate cost, scaling without pain.

What it is:

Move large tables, error lists, and long examples to references, keeping SKILL.md as a short “executive summary.”

Why learn:

It's the guideline you apply when writing your own skill in module 3.6.

Key concepts:

Lean body, in-depth reference, separation of responsibilities.

3.3 ~30 min

🔢 The 6-step framework

Name/trigger, goal, step-by-step instructions, references, rules, improvement cycle — the template every good skill follows.

What it is:

A short, unique name, plus the "trigger" phrase that says when that skill should kick in.

Why learn:

This is the first piece that gets read (Level 1)—if it’s weak, the skill is never called.

Key concepts:

Name, trigger, identification.

What it is:

A sentence that says exactly what the skill delivers when it’s done — “generates a CSV report,” not “helps with data.”

Why learn:

A vague objective leads to vague execution—clarity here prevents rework.

Key concepts:

Objective, success criteria.

What it is:

The numbered sequence of actions the agent should follow — the heart of the skill, equivalent to the “workflow” in the WAT framework (Trail 1).

Why learn:

It's this list that ensures repeatability—the same task produces the same result every time the skill is called.

Key concepts:

Step by step, repeatability, workflow.

What it is:

The list of extra files (Level 3, module 3.2) that the skill can consult when the step-by-step instructions aren’t enough.

Why learn:

Without this declared reference, the agent doesn’t know the detail is there to consult.

Key concepts:

Declared reference, reading pointer.

What it is:

Explicit restrictions—what the skill must never do without confirmation, echoing the safety rules from Track 0.6.

Why learn:

A written rule prevents the agent from “improvising” beyond what you authorized.

Key concepts:

Explicit rule, limit on autonomy.

What it is:

A space set aside to note what went wrong and adjust the steps—the skill isn't born perfect; it gets refined.

Why learn:

Prepares you for module 3.7, where this continuous improvement becomes a regular practice.

Key concepts:

Improvement cycle, iterative refinement.

3.4 ~25 min

🎯 The description is the trigger

How the agent decides to invoke a skill, how to write a description that gets it right, and the most common mistakes in vague descriptions.

What it is:

The agent compares your request with the descriptions (Level 1) of all available skills and chooses the best fit — like a book’s subject index.

Why learn:

Understanding how these work together explains why the right skill sometimes doesn’t activate.

Key concepts:

Intent matching, description index.

What it is:

A good description says “when to use” (trigger) and “what it does” (result), using words someone would actually type — not internal jargon.

Why learn:

It's the difference between a skill that triggers on its own and one that gets forgotten.

Key concepts:

Trigger + result, in the user’s language.

What it is:

Generic descriptions like “helps with documents” mean the skill is never selected because it doesn't stand out from anything else.

Why learn:

Recognizing this error is the first step toward fixing skills that “exist but never trigger.”

Key concepts:

Generic description, ambiguity.

What it is:

Two skills with similar descriptions can confuse the agent about which one to choose—a sign that one of them needs a more specific trigger.

Why learn:

Avoids rework when you already have several skills installed (module 3.5).

Key concepts:

Overlapping triggers, disambiguation.

What it is:

Ask for the same task in different ways (“make a summary,” “summarize this,” “TL;DR this”) and see whether the skill triggers for all of them.

Why learn:

This is the real test of a description’s quality—it’s not enough for it to work with the first phrase you wrote.

Key concepts:

Variation test, trigger robustness.

What it is:

A skill can be called with an explicit command (like /nome-da-skill) or simply by describing what you want in natural language.

Why learn:

Knowing about both options helps you choose which one to use when — a command when you want certainty, natural language when you want fluidity.

Key concepts:

Explicit command, triggered by natural language.

3.5 ~25 min

🗂️ Project vs. global

.claude/skills/ (this project only) vs. ~/.claude/skills/ (all projects) — when to use each one.

What it is:

A folder .claude/skills/ inside the project itself, it stores skills that exist only there—specific to that repository.

Why learn:

Project skills can travel with the code (versioned), so the whole team inherits the same process.

Key concepts:

Project scope, versioned alongside the code.

What it is:

A folder in your home folder (~ = "home") stores skills available in any project you open, on any of your computers.

Why learn:

This is where the personal processes you use all the time live, no matter which project you’re working on.

Key concepts:

Global scope, personal folder (home).

What it is:

Simple rule: if the process only makes sense within this project (e.g., deploying this specific app), it belongs in the project; if it’s something you do anywhere (e.g., generating a summary), it belongs globally.

Why learn:

Putting it in the wrong place is one of the most common mistakes people make when learning skills—it makes it harder to find later.

Key concepts:

Scope criterion, specificity vs. generality.

What it is:

When a project skill and a global skill have the same name/purpose, the project skill usually takes precedence in that context — it's more specific.

Why learn:

Avoids surprises when you expect global behavior but the project overrides it.

Key concepts:

Scope precedence, overlap.

What it is:

How the folder .claude/skills/ lives inside the repository; committing it means every colleague who clones the project automatically gets the same skills.

Why learn:

Turns “the way I do it” into “the way the team does it” without a single meeting.

Key concepts:

Versioned skill, team-wide standardization.

What it is:

Over time, your global folder accumulates skills—it’s worth reviewing it occasionally, deleting the ones you no longer use, and refining unclear descriptions.

Why learn:

Sets the stage for module 3.7, about keeping skills sharp over time.

Key concepts:

Maintenance, periodic cleanup.

🛠️ Build: your first skill

Hands-on: create your first skill from scratch, step by step, with a copy-and-run block.

What it is:

Before writing any skill, choose a task you already repeat manually today—it’s the best candidate to turn into a skill.

Why learn:

A skill that solves a real problem is easier to test and see the benefit of.

Key concepts:

Skill candidate, repetitive task.

What it is:

A ready-to-use block of commands that creates the skill’s folder and starter file, with the front matter already filled in.

Why learn:

This is literally the first practical step—pasting and running it takes away the “blank page anxiety.”

Key concepts:

Initial structure, base template.

What it is:

Fill in the body of SKILL.md using the 6-step framework from module 3.3, with the task you chose in topic 1.

Why learn:

This is where the theory becomes a real, testable file.

Key concepts:

Practical application of the framework.

What it is:

Open a new conversation and describe the task in natural language, checking whether the new skill is actually called.

Why learn:

This is the exercise’s “how to verify”—without this test, you won’t know whether the skill works.

Key concepts:

Trigger check, manual test.

What it is:

A checklist: too vague a description? Folder in the wrong place? Name duplicated by another skill?

Why learn:

Frustration disappears when you have a list of suspects to check instead of guessing.

Key concepts:

Diagnosis, checklist.

What it is:

With the skill working, the natural next step is to use it for real a few times and observe where it fails—module 3.7 opening.

Why learn:

Wraps up this track’s practical cycle before moving on to ongoing maintenance.

Key concepts:

Real-world use, observation, transition.

⚙️ Optimization

Set IDs, preload docs, delegate to subagents, and follow the honest cycle: invoke → observe → fix → repeat. It only gets good around the tenth run.

What it is:

Every skill starts out imperfect: you call it, watch where it gets stuck, revise the text, and call it again. The unvarnished truth: it usually only gets good around the tenth run.

Why learn:

Without this expectation, you give up too soon, thinking the first version should work perfectly.

Key concepts:

Iterative cycle, realistic expectations.

What it is:

Keep file names, sections, and identifiers stable within the skill, even when the content changes — this avoids breaking cross-references.

Why learn:

A skill whose structure changes all the time is hard to maintain and debug.

Key concepts:

Stable ID, cross-reference.

What it is:

When you already know that a reference (Level 3) will almost always be needed, you can instruct the skill to load it right away, without waiting for the agent to "discover" it needs it.

Why learn:

Saves a back-and-forth when Level 3 is virtually guaranteed.

Key concepts:

Preloading, anticipating needs.

What it is:

One subagent is a copy of the agent opened to handle an isolated part of the task, returning only a summary—this way, the skill can delegate heavy tasks without filling up the main context.

Why learn:

Complex skills (e.g., research across many files) get lighter and faster with this trick.

Key concepts:

Sub-agent, context isolation.

What it is:

Looking at it through the WAT framework from Track 1: the SKILL.md is the “workflow” (the step-by-step process), and the scripts/references are the “tools” (the tools the workflow uses).

Why learn:

Ties together everything you learned in both tracks—skills aren’t an isolated concept; they’re WAT applied to a specific process.

Key concepts:

Workflow/tools mapping, track integration.

What it is:

With processes taught through a skill, the next challenge is to run these automations outside your laptop—the subject of Track 4, Deployment.

Why learn:

Wraps up Track 3 with a clear next step in the course.

Key concepts:

Track transition.
