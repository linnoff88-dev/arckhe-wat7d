🍳 The kitchen: recipe, cook, ingredients

New here? WAT it’s the abbreviation that gives this course its name: Workflow + Agent + Tools. Three parts that, together, turn a request in Portuguese into a task that’s actually carried out. To get a firm grasp of the mental model, think of a professional kitchen.

A good kitchen has three separate things: the recipe (the written step-by-step instructions), the cook (the one who reads the recipe, decides on adjustments, and fixes the seasoning) and the ingredients and appliances (what physically exists to become a dish). Remove any one of the three and the kitchen stops working—or becomes something else.

💡 Main Concept

WAT = Workflow (recipe) + Agent (cook) + Tools (ingredients/appliances). Each of the three has a different role, and they don't replace one another.

  • •The recipe doesn’t cook itself — someone has to read and follow it.
  • •A cook without ingredients can only explain the dish, not make it.
  • •Ingredients without a recipe or a cook are just a pantry sitting unused.

The analogy works for any repetitive task, not just cooking. Take an example very different from a newsletter: organizing the month’s receipts for expense reporting. The recipe (workflow) says, “get the receipts from the ‘finance’ folder, sort them by category, total each one, and create a summary spreadsheet.” The cook (agent) decides which category an ambiguous receipt belongs in ("transportation" or "food"?) and notices if a file is corrupted. The ingredients (tools) are the PDF/image reader that extracts the value and the spreadsheet tool that records the summary. None of the three pieces, on its own, organizes any receipts.

🔍 See inside: what happens when the cook reads the recipe

  • What is read: the workflow text (and, if it exists, the project’s CLAUDE.md) becomes part of what the agent “knows” during that run — it uses some of the token quota.
  • What is decided: which tool to call at each step and with what data — this choice isn’t saved by default; it’s made again each time it runs.
  • Where it’s recorded: only the final result (file, spreadsheet, email sent). The "reasoning" in between usually isn't saved unless you ask for a log.
  • How much it costs: each step and each tool call uses tokens — a clear, short workflow costs less than an agent "guessing" from scratch.
2

📋 W for Workflow: the recipe in markdown

New here? Workflow here is simply the written recipe: a sequence of steps in plain text (often in markdown — a way to format text with headings and lists, without complicated code) that says what to do, in what order, and what to check at each step.

A good workflow doesn’t need to anticipate every exception—it just needs to be clear enough so whoever reads it (the agent) knows what to do in the normal flow and recognizes when something goes off track. It's different from a traditional computer program: these aren't rigid, line-by-line instructions, but guidance that someone capable of interpreting them (the agent) will follow with good judgment.

Example of a short workflow, in markdown:

## Workflow: relatório semanal
1. Ler os números de vendas da planilha "vendas.csv"
2. Somar por categoria
3. Escrever um resumo de 3 parágrafos
4. Salvar como "relatorio-semana.md"
5. Se algum número parecer errado (negativo, vazio), avisar antes de salvar

🔍 Inside

  • Markdown: simple text formatting (headings with #, numbered lists)—the same type of file as CLAUDE.md, which you saw in Track 0.
  • Step by step, not code: the workflow is read in Portuguese; it isn’t a programming language.

Another short example, outside the world of email: a workflow for scheduling social media posts could say “read the texts in the ‘posts-da-semana’ folder, generate a cover image for each one, publish one a day at 9 a.m., and let me know if any text exceeds 280 characters.” The recipe doesn’t explain how generate the image or how publish — that’s the tools’ job. It only specifies the order, the exception, and when to stop.

💡 Common error: vague instructions

A workflow like “take care of my finances” isn’t a recipe; it’s a wish. The agent will fill in the gaps with its own assumptions — which may not match what you had in mind. Prefer “read the receipts in folder X, sort them into Y categories, ignore amounts under R$5” over a generic sentence: the more specific the recipe, the less the cook has to guess.

3

👨‍🍳 A for Agent: who reads, decides, and corrects

O agent (agent) is Claude Code — the cook in our analogy. It reads the workflow, interprets each step, decides which tool to use to carry it out, checks the result, and adjusts its course if something didn't match expectations. It's the part that provides judgment to the process: without it, the recipe stays on paper.

This is different from a traditional script (a fixed program that just repeats the same steps without understanding what it's doing). The agent understands the intent behind the “sum by category” step, even if the spreadsheet has an extra column or a different name than expected — it adapts within reason.

✓ What the agent does well

  • ✓Interprets steps written in natural language
  • ✓Choose which tool to use for each step
  • ✓Notices when a result seems wrong and tries again

✗ What the agent does NOT do on its own

  • ✗Guess a recipe that was never written down
  • ✗Using a tool that doesn't exist or that you don't have permission to use
  • ✗Read your mind about what “good” means without you saying it

Common error: the agent “makes up” a path. Imagine a customer service workflow that says “answer questions about orders using the system data” but never says where there’s neither the system nor what to do if the request isn’t found. Without this information, the agent may improvise — respond with a guess — because it was instructed to solve the problem, and “I don’t know” is rarely the first option it tries. The agent isn’t “lying”: it’s filling in a gap the recipe left open. The fix is always in the workflow — say, “if you can’t find the request, stop and ask.”

4

🥕 T for Tools: who actually does the work

Tools (tools) are the ingredients and appliances: the things that actually do the work when the cook calls them — opening a file, running a command, sending an email, searching for something online, calling an API (a communication channel that a website or service leaves open so programs can talk to each other without needing a screen). Without them, the agent would only have opinions, not the ability to act.

A tool without a workflow is practically useless: having an oven on doesn’t make the cake bake by itself — someone (the agent, following the recipe) needs to put the batter in at the right time and temperature. That’s why Tracks 2 (MCP) and 4 (Deploy) in this course are entirely about providing and connecting tools — but they only make sense alongside a workflow that says when to use them.

Common error: the tool’s key is missing. A lot of tools require a API key (a long password that identifies you to the service— Gmail, Google Calendar, a database—configured before it can work. Without it, the tool is stuck: the agent tries to use it, gets an access denied error, and stops there. It’s worth checking before any new automation: does the key exist, is it in the right place, is it still valid? “Tool installed” and “tool authorized to act” are different things—the Trails 2 and 4 show you how to store keys securely.

5

🔗 Why separate the three pieces

Separating workflows, agents, and tools isn't a technical nicety — it's what makes the system predictable enough to trust and flexible enough to be useful. The workflow holds the intent (what to do), the agent stores the judgment (how to interpret and adjust), and the tools store the capacity (what is physically possible to do on the computer or online).

Caption: the recipe comes in from the left, the agent interprets it and activates the tools on the right, and the result cycles back so the agent can decide the next step — this is the loop detailed in module 1.2.

To see all three pieces in action from start to finish, follow a real customer email triage request— a scenario quite different from the newsletter that appears later in the track:

  1. 1. The recipe exists

    The workflow says: “read new emails, classify them as question/complaint/praise, answer simple questions, forward complaints to a human.”

  2. 2. The agent reads and classifies

    Opens the inbox (via a tool), reads each email, and decides on a category—that judgment is its own; the workflow only provided the possible categories.

  3. 3. The tools act

    For a simple question, the email tool sends the standard reply. For a complaint, another tool forwards it to a human and marks it “priority.”

  4. 4. The result is observed

    The agent checks whether the submission was confirmed before moving on — if it fails, it tries again or records the error.

  5. 5. End of the cycle

    If there’s no new email, the agent stops and reports a summary: how many were answered, how many were forwarded.

6

⚖️ Agent without a workflow, tool without a workflow

Two broken combinations explain why all three pieces need to work together. One agent without a workflow it still works, but becomes expensive and erratic: with each request, it reinvents the process from scratch, without learning from last time, and it may take different paths in similar runs. A tool without a workflow is practically useless on its own: an email-sending tool can't decide by itself when or to whom it should send something.

✗ Agent without a recipe

  • ✗Reinvents the process with every request — costly in tokens (the agent’s “currency” for costs, covered in Track 0)
  • ✗Results vary from run to run

✗ Tool without a recipe or a cook

  • ✗It sits idle—the email API doesn't decide on its own when to send
  • ✗No context for “why” you’re using it now

Example of an agent without a workflow: asking “organize my calendar” without details. In one run, it prioritizes work meetings; in another, it prioritizes personal commitments—there’s no recipe setting the criteria. A tool without a workflow would be a perfectly configured post-scheduling tool with a valid key, but no instructions for when to publish what—available, but idle. Both situations reinforce the same lesson: a workflow is what turns standalone capabilities into reliable results.

💡 Practical Tip

Before requesting any automation, write at least 3-4 lines describing the workflow—even informally. It’s the investment that saves the most time and tokens through the rest of the track.
