🎭 Self-correction: truth and marketing

1

🎭 The myth that “it thinks on its own forever”

New here? Self-correction it’s the agent’s ability to notice an error and try again with an adjustment, without you having to say exactly what to fix. It’s real—but it’s often marketed (in videos and product ads) as something bigger than it is: the idea of an AI “thinking on its own forever,” fixing everything, all the time, without limits. This module separates technical facts from marketing exaggeration.

There’s a clear dividing line: in one phase, the agent genuinely tries, makes mistakes, and corrects them flexibly—and in the next, it behaves like any traditional automation, following a fixed script. Confusing the two phases is the source of most broken expectations about “self-managing AI.”

💡 Main Concept

Self-correction has a place: it happens DURING development, with you in control. After publication, the behavior becomes fixed.

Why does this exaggeration catch on so much? Because the most impressive demo there is is watching the agent make a mistake and recover on its own, live, right in front of you. It’s an almost magical effect — and it’s real, which makes it easy to overgeneralize from it. The mistake isn’t thinking self-correction exists; it’s thinking it’s a permanent property of the deployed system, when in fact it’s a property of the work session (the period when Claude Code is open and running, with an active agent reading your messages and deciding what to do next).

Think of two everyday situations for someone taking this course. In the first, you’re building a workflow that downloads invoices from a portal and organizes them in a spreadsheet; the portal changes a button’s text from “Baixar” to “Download” in the middle of the test, the agent tries the old text, fails, reads the error, tries again with the new text, and carries on — all in seconds, while you watch. In second, that same workflow is already published and running every night while no one is watching; months later, the portal changes again, and the workflow simply stops working—without warning, without trying alternative text, without “figuring it out.” Both situations involve the same kind of change. The outcome is opposite because the context is opposite.

2

🔨 During the build: try, fail, fix

While you’re building something in Claude Code—as in the “Build” modules in this course—the agent is actually in a flexible mode: it tries a step, reads the error message if something goes wrong, adjusts its approach, and tries again. This can happen several times in the same session until the result is right. This is the phase behind the reputation of “self-correcting AI”—and within this phase, that’s true.

Example of what happens “under the hood” during construction:

1ª tentativa: comando falha (arquivo nêo encontrado)
   → agente lê o erro, percebe o nome do arquivo estava errado
2ª tentativa: corrige o nome, comando roda
   → resultado bate com o esperado
   → segue para o próximo passo

🔍 Inside

  • Trial, error, correction: the same cycle as module 1.2, but focused on recovering from a specific error.
  • With you in control: this phase is still supervised — you’re there watching and able to interrupt.
  • Cost per attempt: each new attempt uses processing time (and, if you use a paid API, money) — that’s why the agent doesn’t try endlessly; it stops when the result matches or when it seems stuck in a loop.
  • You are the safety boundary: if the attempts start going down a bad path (for example, deleting files it shouldn’t), you’re there in the session to stop it. Once published, that real-time human brake is gone.

A real example of self-correction saving the day, while the automation is still being built: imagine you're asking the agent to build an automation that reads emails from a supplier and extracts the invoice amount. On the first try, it attempts to open the most recent email and breaks because that particular email had no invoice attached (it was just a delivery notice). It reads the error, realizes the filter was picking up any email from the supplier instead of only ones with a PDF attachment, adjusts the filter, and tries again—this time it works. It happened in seconds, without you having to explain the problem. This kind of live recovery is 100% real—and it's exactly what this topic is teaching you to recognize.

3

📦 After publishing: it becomes traditional automation

When the workflow is ready and you set it to run on its own — on a schedule or triggered by an event, without interactive Claude Code open (covered in Tracks 4 and 6) — its behavior changes. It stops "thinking" freely and starts executing the fixed workflow, just like any traditional automation (such as a macro or scheduled script): it follows the written steps without making up new ones.

This is good news, not a limitation: you wants predictability in an automation that runs every day at 7 a.m. with no one watching. A production automation that "thought for itself" and changed its behavior every time would, in practice, be far too unpredictable to trust.

New here? Workflow here means the sequence of steps the agent wrote and tested during the build — the "script" it follows later. Publishing doesn't change the script; it only takes the actor (the agent thinking in real time) off the stage and lets the script run on its own, step by step, like a recording.

A concrete example of the other side of the coin: that same supplier email automation, already published and running every Monday morning. Three months later, the supplier switches email systems, and the messages start coming in with a different subject format. The published workflow won't "notice" and adjust the way it did during development—it simply won't find any emails matching the saved pattern, and it will either fail silently (process nothing without notifying you) or generate an error that only someone checking the logs (the record of what the automation did) will notice. This isn't a system bug—it's the expected behavior of a fixed automation. The self-correction has "used itself up" during development; in production, it's simply no longer there to act.

4

📊 Where the line falls: building × production

The dividing line isn’t about "how smart the agent is" — it’s about where it's running. Within Claude Code, interactively, with you present: flexible mode. Published and scheduled (the subject of Tracks 4 and 6): fixed mode. The table below summarizes the difference directly.

Caption: on the left, the build phase, where the agent adjusts its own approach; on the right, the production phase, where it repeats the recorded workflow without deviating—the line between the two is publication.

Lining up the three phases on a timeline—building, publishing, production—makes it easier to identify, in any of your projects, exactly where the agent’s real-time judgment stops working. It’s this transition, not a drop in “intelligence,” that changes the behavior.

Caption: the arrow runs from building (green, flexible) to production (cyan, fixed), passing through the publication milestone. There is no fourth phase where the agent “goes back to thinking on its own” without you reopening Claude Code.

✓ Before publication

  • ✓Agent reads errors and adjusts its approach on its own
  • ✓You’re present and can interrupt and redirect it
  • ✓The result may vary across attempts until it’s right

✗ After publishing

  • ✗A new error doesn’t become “attempt 2”—it becomes a recorded failure
  • ✗No one is watching in real time to interrupt
  • ✗The same step-by-step process repeats until you go back and edit
5

📣 Why marketing exaggerates

Videos and sales materials often show only the build phase — the most impressive part, with the agent fixing errors on the spot — and imply that this continues indefinitely after publishing. That's not a lie about what happened in the demo; it's an overgeneralization about what happens afterward. Understanding this difference prevents two common frustrations: thinking that a published automation will “take care of itself” forever, or doubting the entire course when that doesn't happen.

⚠️ Attention

A published automation that starts failing (for example, because a website changed its structure) will NOT fix itself — it will fail the same way every time until someone (you, in Claude Code) comes back and adjusts the workflow. This is expected, not a defect.

Three mental traps come up often for beginners, and it’s worth naming each one:

Error 1 — “Fixed it once, so it’s guaranteed forever”

Seeing the agent recover from an error during the build isn’t evidence that it will recover from the next error, in production, on its own. Every correction during development was made with you there — none of them are “stored” as a permanent skill in the published workflow.

Error 2 — Publishing without testing the error path

It's common to test only the “happy path” (when everything goes right) before publishing, and never test what happens when data is missing, a site is down, or a file doesn't exist. In production, without self-correction, it's precisely this error path that determines whether the automation fails gracefully (by notifying you) or fails badly (by freezing or silently deleting something).

Error 3 — Assuming you don’t need to check again after publishing

Because the build phase was so “smart,” it’s tempting to treat the published automation as if it kept taking care of itself. It doesn’t—periodic checks (Track 4, observability) are what replace, in production, the real-time judgment that existed during the build.

💡 Practical Tip

Before publishing any workflow, deliberately cause at least one error (delete some data, turn off Wi-Fi, point to a file that doesn’t exist) and see what happens. If it fails silently, adjust the workflow to notify you—while it’s still easy to fix.

6

🎯 What to expect in practice

In practice, use the build phase to make the workflow robust — that's when it's worth testing variations and edge cases, and letting the agent iterate until it gets things right. After it's published, monitor it (Track 4, observability module) to know when something changes out there and the workflow needs maintenance — but don't expect an automatic fix at that point.

💡 Practical Tip

Treat the build phase as "practice" and publishing as the "test." Spend plenty of time testing during practice — that’s where self-correction works in your favor for free.

A simple way to make this a habit: whenever you finish building a workflow and before publishing it, ask the agent itself to list, in writing, "what could go wrong here in production, and what happens in each case." You don't need to know how to code to understand the answer—you just need to decide whether each scenario listed is acceptable (the workflow stops and alerts you) or dangerous (the workflow continues and does something wrong silently). Making this request while the agent is still supervising the session is the last window when real self-correction can still work in your favor before publication.

Ask the agent this before publishing (copy and paste):

Antes de eu publicar este workflow, liste os pontos onde ele pode
falhar em produçêo (site fora do ar, dado faltando, formato mudou)
e diga, para cada um, se o workflow para com um aviso claro
ou continua rodando de um jeito que pode causar erro silencioso.
