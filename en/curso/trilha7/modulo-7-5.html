💾 Backup and version control: protecting your assistant’s home

In the previous phases, you built a house and gave your assistant life, hands, and room to grow. Now protect all of that: months of context, decisions, and preferences can't disappear because of one wrong click, a hard drive failure, or a file accidentally deleted. This module is insurance for the employee you just trained.

🏚️ Why this matters specifically here

Your assistant’s folder isn’t an ordinary folder. It’s its home — where the CLAUDE.md (the brain with its permanent instructions, covered in module 0.4), the context notes it has accumulated, the preferences you adjusted phase by phase (Home, Life, Hands, Growth), and the decisions recorded over months. Losing that folder doesn’t mean losing “a few files”: it means losing an entire employee you trained with time and attention.

Think of the opposite of hiring someone and, three months later, that person getting hit on the head and forgetting everything they learned about your routine, preferences, and house rules. That’s rare with a human employee. With a folder of files on an ordinary laptop, it happens much more often than you might think—a corrupted hard drive, cloud sync that overwrites files, accidental deletion during a disk cleanup.

💡 Main Concept

Your assistant’s folder is an asset, not a technical detail. It holds invested time that you can’t recreate in an afternoon.

  • •The more months you use it, the more costly it becomes to lose it—the cost of rebuilding grows with the value accumulated.
  • •Protecting this folder is part of the work of "owning" the assistant, not an optional extra for later.

📜 Versioning, in plain English

New here? You already used versioning without knowing the name: in Google Docs, every change is saved in a “version history” — you can open the document as it was yesterday or a month ago, and revert if something went wrong. Version control is exactly that, but for an entire folder of files: a system that saves every change, with the date and a summary of what changed, so you can roll back when you need to.

The tool most commonly used for this is called git — a version control (the technical name for the category). You don’t need to understand the engineering behind it: what matters is the concept—each time you “save a milestone” (this is called commit, a snapshot of the folder at that moment), git keeps that snapshot forever. If a context file gets messy, you can look at earlier snapshots and restore the good version.

Caption: each green dot is a commit — a saved snapshot of the folder on that day. If something breaks after “today,” you can return to the highlighted recovery point without losing everything that came before.

🔍 Inside

  • Commit: a saved “snapshot” of the folder, with a short sentence saying what changed.
  • History: the row of all photos, in order — you can see “what changed and when” for any file.
  • Go back: ask to restore an earlier photo without losing the rest of the history.
3

🧱 Two layers of protection, not one

New here? Backup is just a backup — a second copy of the entire folder stored somewhere else, locally (on an external hard drive, for example) or in the cloud (an online storage service like Google Drive or Dropbox). It solves the "everything disappeared" problem: if the computer breaks or the original file is deleted, you have a copy to recover from.

Git version control is something else, and the two complement each other. A backup restores the entire folder after a total disaster; git gives you a line-by-line history—the “what changed and when” inside context and decision files, even if nothing has “disappeared.” Having only backups and never using version control is like having fire insurance but no way to know what you changed yesterday. Having only git and never backing up off the machine means trusting that the drive will never die—it will, sooner or later.

Caption: the folder at the bottom is the asset; the backup (middle) protects against “everything disappeared”; the version history (top) protects against “something changed and I don’t know what” — together, the two layers cover both risks.

✓ Both layers together

  • ✓Hard drive fails → you restore from the backup
  • ✓Context file became confusing → you check the history and restore the good version
  • ✓Want to know “what changed last week” → the history has the answer

✗ Just one layer

  • ✗Backup only: no detailed visibility into what changed between copies
  • ✗Git only: a drive that fails without an external backup takes the history with it
  • ✗Neither: a single point of failure determines the fate of months of work

🔧 Step by step: setting up the two layers

You don’t have to know the terminal by heart to do this — Claude Code itself can configure both layers for you if you ask clearly. The steps below assume no prior knowledge.

1

Open a terminal in the assistant’s folder

O terminal it’s the text box where you give commands directly to the computer (covered in module 0.2)—nothing changes here from what you already do every day.

2

Ask Claude Code to configure version history (git)

Use the copy-run block below. It turns the folder into a version-controlled repository without you having to type any commands by hand.

3

Set up the backup in a second location

Local (external hard drive, USB flash drive) or in the cloud (a folder synced with a storage service). The important thing is that it stays outside on the same disk where the original folder lives.

4

Confirm that both are working

See the "how to verify" section of the copy-run block — configuring it once isn’t enough; you need to confirm that the commit and the copy actually happened.

COPY-RUN · prompt for Claude Code Paste and run 
Configure backup e versionamento para a pasta deste assistente.

Objetivo: proteger tudo que está aqui (CLAUDE.md, contexto,
decisões) contra perda, com duas camadas.

1. Inicialize um repositório git nesta pasta, se ainda nêo
   existir, e faça um primeiro commit com tudo que já está aqui.
2. Crie um arquivo .gitignore básico (excluindo segredos, chaves

3. Sugira um comando simples que eu possa rodar toda semana para
   salvar um novo commit ("checkpoint semanal").

   segurança desta pasta inteira em <meu HD externo ou serviço

5. Ao final, me diga como eu confirmo que o histórico de versões
   está funcionando (que comando roda para ver o histórico).

✅ How to verify

Ask the agent to list the commit history — if at least one item appears with a date and a phrase describing the change, version control is active. For the backup, open the second location (drive or cloud folder) and check that the latest files are there with today's date.

📅 Routine: when to do what throughout the month

Backup and version control only work if they become routine — configuring them once and never touching them again is almost as bad as having nothing. The frequency below is INEMA’s recommendation for a folder used by an active assistant.

Daily

Quick commit at the end of a day of use

If you changed CLAUDE.md or a context file today, a short commit (“adjusted time preference”) creates a recovery point. It takes less than a minute if you ask the agent.

Weekly

Weekly checkpoint + history review

Once a week, review the week's commits — confirm that the history makes sense and catch any forgotten commits.

Monthly

Complete backup verified

Once a month, confirm that the backup is up to date and — the step almost everyone skips — actually test whether you can open a file from it.

💡 Practical Tip

Ask the assistant itself to remind you: "every Friday, ask me if I've done the weekly checkpoint yet". This connects to module 6.2 (scheduled tasks) — the protection routine can become automatic instead of relying on your memory.

⚠️ Costly mistakes

Most data disasters aren’t caused by a lack of tools — they come from a bad habit. The two pairs below cover the most common mistakes INEMA sees at this stage of the course.

✓ Simple backup routine

  • ✓Monthly copy stored off the original drive, actually tested
  • ✓Alert or reminder set up—it doesn’t depend on your memory

✗ Never having a backup

  • ✗"My computer has never had a problem" — until the day it does
  • ✗Only one place storing months of context and decisions

✓ Have both: saving + history

  • ✓"I saved the file" ensures the current edit won't disappear
  • ✓"I have version history" means you can recover yesterday’s version if today’s one has a problem

✗ Confusing “I saved it” with “I have a history”

  • ✗Thinking Ctrl+S solves everything — it only saves the present, not the past
  • ✗Discovering you needed the “previous version” only after you'd already overwritten it

⚠️ Attention

Never commit (or back up) API keys, passwords, or credentials in plain text inside the git repository — if that history is ever shared or leaked, those credentials stay exposed in the history forever. Keep them in separate files excluded by `.gitignore`, as the prompt in topic 4 already asks.
