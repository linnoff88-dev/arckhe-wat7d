TRACK 4

🚀 Deploy: getting off your laptop

So far, everything your Digital Employee has done has run because your computer was on, with the terminal open. That’s not automation—it’s you pressing the button again every time. In this learning path, automation moves off your plate and starts running on its own in the cloud, 24 hours a day, with secrets stored securely and a way for you to find out what went wrong without understanding a single line of code.

Caption: the code leaves your laptop, passes through git to the repository, and is pulled by the cloud platform that runs the automation on its own; everything that happens is recorded in a dashboard you can read without knowing how to code.

4.1~25 min

💻 Why local isn’t enough

A button that only works when you’re nearby isn’t automation—it’s a shortcut. Here, you’ll understand the difference.

What it is:

If your automation stops working when you close your laptop, it’s not automation yet—it’s a script you trigger yourself.

Why learn:

This is the quickest test to see whether something is ready to become a real routine or still depends on you.

Key concepts:

Local execution, requiring your presence, “run on its own.”

What it is:

The cloud is a computer owned by another company, always on, rented by usage — your automation runs there, not in your room.

Why learn:

Understanding this shift in “where it runs” is the foundation for making sense of everything else in the learning path.

Key concepts:

Remote server, 24/7 availability, pay-per-use cost.

What it is:

One-off tasks that you trigger yourself ("organize this folder now") don’t need any deploy.

Why learn:

Publishing everything to the cloud unnecessarily creates extra work and extra cost for no reason.

Key concepts:

One-off task vs. recurring routine.

What it is:

Claude Code writes the code, git takes it to the repository (GitHub), and a hosting platform pulls and runs that code in the cloud.

Why learn:

This is the complete map that module 4.2 will explain step by step.

Key concepts:

Repository, execution platform, pipeline.

What it is:

The agent writes the code; your skill in this track is reading the result and the log — not writing TypeScript.

Why learn:

Takes away the fear that “I need to become a programmer” to publish real automations.

Key concepts:

Reading logs, reviewing, delegating code writing.

What it is:

Pipeline → dev/production → secrets → retries → hands-on build → observability.

Why learn:

Seeing the complete path helps you avoid getting lost in the middle of a new, technical topic.

Key concepts:

Learning path progression, dependencies between modules.

🚉 The pipeline in 4 stages

Code, repository, platform, execution — four stops that take your automation from your laptop to the cloud.

What it is:

You ask for the task in Portuguese, and the agent writes the "recipe" in TypeScript — a programming language used by these execution platforms.

Why learn:

Knowing this step exists (and that you don’t write it) takes away the fear of “I don’t know how to code.”

Key concepts:

TypeScript, task (a task in code), assisted writing.

What it is:

Git sends the code to the repository—an online vault (GitHub) that stores every version of your project.

Why learn:

It's this step that the execution platform watches: when something new arrives there, it reacts.

Key concepts:

git, repository, push (the command that sends it).

What it is:

A runtime platform (we use Trigger.dev in this course) pulls this code from the repository and runs it on its own servers, without relying on your computer.

Why learn:

It's the station where automation truly “comes to life on its own.”

Key concepts:

Execution platform, deploy, cloud environment.

What it is:

After it runs, the platform records everything in a log that you can monitor from the dashboard—without needing to look at the code.

Why learn:

It's the skill that replaces “knowing how to code”: knowing how to read this output.

Key concepts:

Log, dashboard, execution result.

What it is:

At each stage, you ask, review, and approve—the agent does the heavy lifting of writing code.

Why learn:

Defines exactly where your attention is needed and where you can trust the process.

Key concepts:

Review, approval, supervised delegation.

What it is:

Write → send → run → record. A short cycle that repeats with every change you approve.

Why learn:

Mastering this cycle is what makes you comfortable publishing any automation from here on out.

Key concepts:

Deploy cycle, repeatability.

🧪 Testing vs. production

Two environments, the same automation—one for you to break as much as you like, the other that no one touches without care.

What it is:

A copy of the automation running separately, where errors don’t affect anyone in the real world.

Why learn:

This is where you test changes before putting them into effect for real.

Key concepts:

Test environment (dev/staging), isolated copy.

What it is:

The environment that actually runs, handling real data and sending real things (emails, spreadsheets, messages).

Why learn:

Errors here have real consequences—which is why it’s important never to test directly on it.

Key concepts:

Production environment, real data, real action.

What it is:

The same code runs in both environments; what changes are the settings and secrets used in each one.

Why learn:

You don’t have to duplicate your work — just point to the right environment before publishing.

Key concepts:

Same code, environment-specific configuration.

What it is:

Only goes to production after running without errors in the test several times, with data similar to real data.

Why learn:

Avoids the shock of discovering a bug after real data has already been affected.

Key concepts:

Promotion criterion, repeated testing.

What it is:

Plan mode (introduced in module 0.5) asks the agent to show what it’s going to do before acting — here, a production bug isn’t just ugly; it costs you duplicate data.

Why learn:

Making this specific requirement for production changes a habit is what separates safe sessions from risky ones.

Key concepts:

Plan mode, review before taking action, cost of errors in production.

What it is:

Tested in the test environment, reviewed the plan, checked the secrets for the right environment—only then promote it.

Why learn:

A short checklist helps you remember the step that hurts most to forget.

Key concepts:

Promotion checklist.

4.4~25 min

🔑 Secrets

An API key is like a bank password: it never goes with the code into a public repository.

What it is:

Any information that grants access to something — an API key, password, token — and must not leak to anyone.

Why learn:

Cloud automation always uses secrets to communicate with other services—protecting them is mandatory.

Key concepts:

Secrets, API key, access token.

What it is:

The file .env stores your secrets locally and stays out of what gets sent to the repository.

Why learn:

Repositories can accidentally become public—a secret leaked there is practically impossible to take back.

Key concepts:

.env file, .gitignore (list of things that should never be uploaded).

What it is:

The keys are entered directly in the execution platform’s dashboard, in a protected field—never in the code.

Why learn:

This is the only way for the automation to access the secret without it ever passing through the repository.

Key concepts:

Manual setup, in a protected dashboard field.

What it is:

The test secret and the production secret are set up separately — each environment has its own key.

Why learn:

That way, a wild test never touches the real production account or service.

Key concepts:

Per-environment secret, credential isolation.

What it is:

Rotation means generating a new key and disabling the old one — the fix for an exposed secret.

Why learn:

Knowing the next step keeps a scare from turning into a bigger problem.

Key concepts:

Key rotation, revocation.

What it is:

.env outside the repository, keys configured in both environments, no secrets in screenshots or messages.

Why learn:

A short checklist becomes a habit and helps prevent the costliest mistake on this learning path.

Key concepts:

Secrets security checklist.

4.5~30 min

🔁 Retries and queues

Small tasks fail small. Why breaking work into pieces is the difference between a hiccup and a mess.

What it is:

Connection drops, external service slows down, server restarts—temporary failures are normal in the cloud.

Why learn:

Accepting that failures will happen changes how you design the automation from the start.

Key concepts:

Transient failure, network instability.

What it is:

Retry is the platform automatically trying again to complete a step that failed, without you having to restart everything.

Why learn:

This is the mechanism that lets the automation recover from temporary failures without your intervention.

Key concepts:

Retry, automatic attempt.

What it is:

If the entire automation is one block, a failure halfway through means redoing everything—including the parts that already worked.

Why learn:

Breaking it into small steps means only the step that failed needs to be repeated.

Key concepts:

Breaking it into steps, task granularity.

What it is:

Separating the step that fetches data from the step that saves it prevents a retry from saving the same thing twice.

Why learn:

This is the design that prevents the most common problem with poorly planned automation: duplicate entries.

Key concepts:

Fetch/save separation, duplicate prevention.

What it is:

A queue holds pending tasks in order, processing them one at a time — like a bank line, but for work.

Why learn:

Queues prevent overload when many tasks arrive at once.

Key concepts:

Queue, sequential processing.

What it is:

Small tasks + automatic retries + separate fetching from writing.

Why learn:

This is the summary you can ask Claude Code to apply whenever you design a new automation.

Key concepts:

Resilience, design principles.

🛠️ Build: publish a scheduled automation

Hands-on module: write, test, add a secret, publish, and schedule — from scratch to running in the cloud.

What it is:

Your first release should be small — something like emailing a daily summary.

Why learn:

Starting simple reduces the number of things that can go wrong during your first deployment.

Key concepts:

Small scope, first deploy.

What it is:

A clear prompt describing what the automation should do, when it should run, and what it needs access to.

Why learn:

The clearer the request, the fewer back-and-forths it takes to get the code right.

Key concepts:

Task prompt, scheduling.

What it is:

Run the task in the test environment with a test secret, and check the log.

Why learn:

It's the step that keeps an error from going straight into the real world.

Key concepts:

Test in dev, check the log.

What it is:

Repeat the secret setup, this time in the production environment, using the service’s real key.

Why learn:

Without this, the published automation runs in production but fails because it lacks credentials.

Key concepts:

Production secret, configuration dashboard.

What it is:

The deploy command uploads the code that has already been tested to the platform’s production environment.

Why learn:

This is when the automation truly comes to life, outside your computer.

Key concepts:

Deploy, production release.

What it is:

After deployment, confirm in the dashboard that the automation is scheduled, then wait for the first automatic run.

Why learn:

Seeing it run on its own, without you touching anything, proves that the whole workflow worked.

Key concepts:

Schedule confirmation, first automatic run.

📊 Observability

You don’t need to know TypeScript — you need to know how to read the dashboard and find where things broke.

What it is:

A dashboard is the platform's web page where you can see all the runs of your automation.

Why learn:

This is the only place where you can “see” what’s happening in the cloud.

Key concepts:

Panel, dashboard, run list.

What it is:

The log is the ordered list of everything the automation did — like a captain’s log.

Why learn:

Reading the log is the skill that replaces “knowing how to code” throughout this entire learning path.

Key concepts:

Log, recorded event.

What it is:

Failures are often highlighted in red in the log — it’s the first place to look when something goes wrong.

Why learn:

Avoids reading the entire log line by line when the problem is already flagged.

Key concepts:

Highlighted error, point of failure.

What it is:

Copy the log snippet with the error and paste it into a conversation with the agent, asking it to explain and fix it.

Why learn:

You don’t have to figure out the error on your own — you need to know where to find it and bring it to the right agent.

Key concepts:

Assisted diagnosis, guided correction.

What it is:

Many platforms send you an email when a run fails, so you don’t have to keep checking the dashboard.

Why learn:

This is what turns observability from a “manual task” into an “automatic habit.”

Key concepts:

Alerts, failure notifications.

What it is:

You went from “it only works on my laptop” to “it runs on its own, with protected secrets and a way to check the automation's health.”

Why learn:

It's the foundation for the next tracks, which assume your automation can already run in the cloud.

Key concepts:

Deploy, observability, next track.
